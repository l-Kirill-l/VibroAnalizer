# VibroAnalyzer v2 — архитектура

## Назначение

VibroAnalyzer v2 — универсальная измерительная платформа, использующая звуковую
карту как АЦП/ЦАП. Программа не привязана к вибрации: через неё можно измерять
медицинские сигналы, сейсмологию, акустику, музыкальные сигналы, датчики износа
и любые другие сигналы, которые можно подать на аудиовход.

`VibroWaveLab` — только запускалка. Программа полностью работает автономно.

## Проекты

| Проект | Назначение |
| --- | --- |
| `src/VibroAnalyzer.Core` | Сигналы, устройства, DSP, модуляция, анализаторы, калибровка, сессии, `AudioEngine` |
| `src/VibroAnalyzer.Audio` | Бэкенды: `Simulated`, `PipeWire`, `WASAPI`, фабрика |
| `src/VibroAnalyzer.App` | Avalonia UI: главное окно и отдельные окна анализаторов |
| `tests/VibroAnalyzer.Tests` | xUnit-тесты DSP, модуляции, сессий, движка |

Зависимости направлены только внутрь: `App → Audio → Core`, `App → Core`,
`Tests → Core/Audio`.

## Маршрутизация: логические шины

Один физический канал — одна или несколько логических шин.

| Тип | Назначение |
| --- | --- |
| `InputBus` | физический входной канал → моно-сигнал, демодуляция, анализаторы |
| `OutputBus` | независимая несущая/модуляция → физический выходной канал |
| `VirtualInputBus` | объединение нескольких входов (среднее, сумма, полосы) |

На один физический канал можно создать несколько шин. Например, два
`InputBus` на канал 0 — для двух окон с разными настройками; несколько
`OutputBus` на канал 0 — их сигналы складываются в `OutputMixer`.

### Вход

```
устройство → IAudioStream.InputAvailable → InputBus.Process (выделение канала)
    → RawBuffer → анализаторы (Source=Raw)
    → DemodulationChain → DemodBuffer → анализаторы (Source=Demodulated)
```

Каждый `InputBus` держит собственные буферы на 5 секунд, собственный
`AnalyzerHost` (таймер 50 мс) и собственную `DemodulationChain`.
Анализаторы и окна привязываются к шине, а не к движку целиком.

### Выход

```
OutputBus.Modulation.GenerateBlock → OutputMixer.Mix → IAudioStream.Write
```

`OutputMixer` собирает моно-сигналы выходных шин в интерливленный блок
устройства. Разные шины могут занимать разные физические каналы; несколько
шин на одном канале суммируются с ограничением по уровню.

### Виртуальные входы (микширование датчиков)

`FusionMode`: `Average`, `Weighted`, `Sum`, `Difference`, `Minimum`,
`Maximum`, `BandMerge`. Источники задаются `FusionSource` с усилением,
полосой (`Full`, `LowPass`, `HighPass`) и частотой среза. Типичные сценарии:

- среднее или взвешенное среднее нескольких датчиков;
- разность сигналов;
- объединение НЧ- и ВЧ-датчиков в широкополосный канал (`BandMerge`);
- общий минимум/максимум для контроля перегрузки.

`VirtualInputBus.Update` берёт у каждого источника только новые отсчёты
(`SignalRingBuffer.TotalFramesWritten`) и пишет в свой буфер непрерывный
поток. Это важно: повторная склейка перекрывающихся снимков давала бы
разрывы и широкополосный «мусор» в спектре.

### Окна и привязка

- `ScopeWindow`/`SpectrumWindow` создают собственный анализатор и добавляют
  его в `ISignalBus.AddAnalyzer`. На одну шину можно открыть несколько окон —
  например, два осциллографа с окнами 5 мс и 200 мс.
- `DemodulationWindow` привязано к `DemodulationChain` конкретной шины.
- `ModulationWindow` привязано к `ModulationChain` конкретного `OutputBus`.
- `OverlayWindow` показывает временные формы и спектры нескольких шин на
  общих графиках с цветной легендой.

### Модуляция и демодуляция

- Включаются и настраиваются независимо для каждой шины.
- Модуляция: синус/прямоугольник/треугольник, амплитудная модуляция внутренней
  синусоидой, глубина и амплитуда базы.
- Демодуляция: огибающая или синхронная (I/Q с оценкой амплитуды и фазы).
- Можно как генерировать собственную несущую, так и принимать уже
  модулированный внешний сигнал.

### Несколько устройств

Движок группирует шины по `DeviceId`:

- вход и выход на одном устройстве → один дуплексный поток;
- только вход или только выход → поток в одну сторону;
- разные устройства → отдельные потоки.

Каждая группа получает собственный таймер выхода. Для компенсации дрейфа
и фазы между устройствами зарезервировано место в настройках; текущая версия
использует общий номинальный `SampleRate` и предупреждает о дрейфе.
Ресемплинг источников с разной частотой пока не выполняется — шины должны
работать на одной частоте.


## Устройства и возможности

`AudioDeviceInfo` описывает:

- направления (`IsInput`, `IsOutput`, `IsDuplex`);
- число каналов, частоты по умолчанию и поддерживаемые;
- назначение каналов и тип разъёма (`AudioChannelInfo`, `AudioJackType`);
- `DeviceCapabilities`: дуплекс, AC/DC-связь, допустимое напряжение,
  эксклюзивный режим, loopback, переназначение каналов, примечания.

UI показывает возможности и предупреждает, например, о выборе monitor-источника.

## Калибровка

`CalibrationProfile` пересчитывает нормализованные отсчёты:

```
volts = normalized * FullScaleVolts / InputGain
Voltage   → volts / SensorSensitivity
Current   → volts / ShuntOhms / SensorSensitivity
Physical  → volts / SensorSensitivity
```

Единицы: В, А или физическая единица датчика. Аппаратная реализация датчиков —
зона пользователя; программа даёт подсказки и предупреждения.

## Анализ

`AnalyzerHost` работает отдельно для каждой шины. Окна осциллографа и спектра
создают собственные экземпляры анализаторов; на одну шину можно открыть
несколько окон с разными параметрами. Каталог «Анализаторы» содержит 29
анализаторов по категориям (общие измерения, акустика, электрика, музыка,
диагностика, вибрация, сейсмология, медицина), описание и кнопку «?» с
подробными формулами, допущениями и ограничениями.

## Запись и воспроизведение

- «Записать сессию» сохраняет все входы, виртуальные входы и мониторы выходов.
- «Запись» у конкретного входа/микшера сохраняет только его raw/demod.
- Формат: моно IEEE float32 WAV + `manifest.json` в автоматически созданной
  папке `recordings/<дата-время>-<имя>/`.
- «Открыть запись...» или `--replay <папка>` открывает окно воспроизведения:
  транспорт, перемотка, скорость 0.25×…4×, окна всех анализаторов.
- При воспроизведении данные берутся из файлов, физические устройства не
  используются; после Seek в буферы предзагружается до 20 с истории.

## Сессии и отчёты

`SessionContext` разбирает аргументы:

```
--session-dir <путь>
--session-dir=<путь>
--module-id <id>
--module-id=<id>
```

Без `--session-dir` используется `./SharedSessionData`, режим считается
автономным. `SessionWriter` пишет:

- `SharedSessionData/<moduleId>/report.json` — отчёт с измерениями и пиками;
- копию `report-yyyyMMdd-HHmmss.json`;
- `status.json` — состояние модуля;
- `SharedSessionData/session_state.json` — общий журнал измерений в формате,
  совместимом с UE5, с блокировкой и атомарной записью.

## Бэкенды

- **Демо** — включается в окне «Настройки», генерирует сигнал по конструктору
  тонов (частота, амплитуда, форма, канал) и шуму. Используется в тестах и при
  отсутствии оборудования.
- **PipeWire** — Linux, `pactl` для перечисления устройств, `parec`/`pacat`
  для потоков. Формат float32le, явные `--rate`, `--channels`, `--latency-msec`.
  `pw-dump` (с запасным вариантом `pactl -f json list cards`) даёт физические
  разъёмы и их доступность.
- **WASAPI** — Windows, NAudio: `MMDeviceEnumerator`, `WasapiCapture`,
  `WasapiOut`, фактический формат микшера, конвертация float/PCM.

Фабрика `AudioBackendFactory` выбирает первый доступный бэкенд, иначе демо.

### Карта → порт → канал

PipeWire перечисляет не только узлы source/sink, но и отдельные физические
маршруты карты. Программа строит иерархию:

```text
Карта
  ├─ входной порт
  │    └─ каналы 1..N
  └─ выходной порт
       └─ каналы 1..N
```

- `Карта` — физическая карта/кодек, например `ALC256 Analog`.
- `Порт` — физический вход или выход: `Встроенный микрофон`, `Микрофон гарнитуры`,
  `Динамики`, `Наушники`, `Вход 3 · XLR`, `ADAT 1–8`.
- `Канал` — физический канал внутри порта: моно, левый/правый, 1–8 для ADAT.

Основные списки больше не содержат выбора устройства и номера канала. Входы и
выходы создаются как логические объекты:

- «Добавить датчик» создаёт строку в состоянии «не подключён»;
- «Добавить выход» создаёт выход с параметрами модуляции;
- кнопка «Подключение» в строке раскрывает каскад `карта → порт → канал`;
- выбранный порт активируется через `pactl set-source-port` / `set-sink-port`;
- после подключения в строке отображается физическая цепочка:
  `ALC256 Analog · Встроенный микрофон · моно`;
- несколько логических датчиков могут ссылаться на один физический канал;
- при смене подключения имя, анализаторы, запись и окна датчика сохраняются.

Мультиплексирование портов пока не учитывается: если два датчика выбирают
разные порты одного потока, драйвер оставит активным последний выбранный.

### Инспектор карты и порта

Справа карточка `Карта и порт` не зависит от маршрутизации. В ней выбираются
карта и порт, а таблица показывает физические каналы:

```text
КАНАЛ | НАЗНАЧЕНИЕ | ИСПОЛЬЗУЕТСЯ | УРОВЕНЬ
1     | микрофонный вход | Датчик 1 | -18.2 dB
```

- `НАЗНАЧЕНИЕ` — микрофон/линия, левый/правый, цифровой канал;
- `ИСПОЛЬЗУЕТСЯ` — имена логических датчиков/выходов на этом канале;
- `УРОВЕНЬ` — RMS по последним данным соответствующей шины;
- число строк равно числу каналов выбранного порта.

Мониторы PipeWire (`*.monitor`) — это петля выхода, а не физический вход.
Они исключены из списка физических карт, чтобы не выглядеть как «два микрофона».

### Поиск сигнала

В панели подключения входа есть кнопка «Найти сигнал». Она сканирует все
выбранные карты и входные порты, после чего показывает массив отреагировавших
каналов:

```text
Карта | Порт | Канал | Уровень | Занято
```

Есть фильтры по карте и входному порту, порог в dBFS. Сигнал может появиться
на нескольких каналах из-за акустической/вибрационной связи — показываются все
варианты, пользователь выбирает нужный вручную. Для одного потока выбирается
активный физический порт, чтобы не дублировать один и тот же уровень.

## Сборка и запуск

```bash
dotnet build VibroAnalyzer.slnx
dotnet test tests/VibroAnalyzer.Tests/VibroAnalyzer.Tests.csproj
dotnet run --project src/VibroAnalyzer.App
```

Запуск с сессией:

```bash
dotnet run --project src/VibroAnalyzer.App -- \
  --session-dir /path/to/SharedSessionData --module-id hw_vibro_analyzer
```

Демонстрационный режим (2 входа, 2 выхода, среднее датчиков) и сразу старт:

```bash
dotnet run --project src/VibroAnalyzer.App -- --demo --start --open=scope,spectrum,overlay
```

Демо-режим включается в окне «Настройки»: там же находится конструктор
частот/колебаний. В обычном режиме приложение показывает реальные устройства
ввода/вывода ПК, включая физические каналы без подключённого сигнала.

## Ограничения текущей версии

- Калибровка пока задаётся через API, отдельного окна калибровки нет.
- Компенсация дрейфа/фазы для разных устройств зарезервирована, но не
  реализована как отдельный алгоритм; ресемплинга между разными частотами нет.
  При несовпадении частоты устройства и выбранной в программе движок выдаёт
  предупреждение.
- Спектрограмма (водопад), кросс-спектр, когерентность и передаточная функция
  требуют отдельных многоканальных/двухвходовых окон и пока не реализованы.
- Микшер настраивается через окно выбора каналов (усиление, полоса, режим);
  полноценного редактора графа источников пока нет.
- Прямое управление кодеком/пинами не выполняется: только штатные API и
  существующие утилиты ОС.
